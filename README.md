# 掲示板アプリケーション (bulletinboard)

## 0. プロジェクトの目的
- Spring Boot を使用した Web アプリケーション開発の学習
- Java によるサーバーサイド処理と、画面表示（フロントエンド）の連携の流れを理解する

## データベース設計の自動化について
本プロジェクトでは、学習の効率化のため `spring.jpa.hibernate.ddl-auto` 設定を利用し、JavaのEntityクラスからデータベーステーブルを自動生成しています。

*   **意図**: 本来必要なSQLによるテーブル作成手順を自動化することで、Javaによるサーバーサイド処理や画面連携の実装に集中するためです [1, 2]。

## 開発中に発生したエラーと解決記録（2026/07/21）


Spring BootとMySQLの連携にあたり、以下の3つのエラーに直面し、それぞれ解決しました。

### 1. MySQLドライバーの未検出エラー
* **事象**: `Cannot load driver class: com.mysql.cj.jdbc.Driver`
* **原因**: 初期設定の `pom.xml` にMySQLと接続するためのライブラリ（JDBCドライバー）が用意されていなかったため、JavaとMySQLが通信できませんでした。
* **解決策**: `pom.xml` に `mysql-connector-j` の依存関係を追加し、システム間の「通訳」を配置しました。

### 2. 旧バージョン用Hibernate方言（Dialect）の廃止エラー
* **事象**: `Unable to resolve name [org.hibernate.dialect.MySQL8Dialect]`
* **原因**: `application.properties` に記述されていた古い形式の方言設定（MySQL8Dialect）が、使用している新しいバージョンのHibernateで完全に廃止・削除されていたためです。
* **解決策**: 設定を最新の共通規格である `MySQLDialect` に変更（または削除による自動判別化）し、新しい言語変換に対応させました。

### 3. MySQLセキュリティによる公開鍵の回収拒否エラー
* **事象**: `Unable to open JDBC Connection for DDL execution [Public Key Retrieval is not allowed]`
* **原因**: MySQL 8.0以降の安全対策により、Java側からの暗号化通信用「公開鍵」の自動要求がデフォルトでブロックされたため、ログインを門前払いされました。
* **解決策**: 接続URLの末尾に `allowPublicKeyRetrieval=true` を明示的に追記し、安全なアクセス鍵の回収を許可しました。

---

### 2. DTO（RegisterForm）導入による設計の最適化
* **事象・課題**:
  * パスワードを暗号化（ハッシュ化）して保存する際、ハッシュ化後の文字列（60文字）に対してDB保存直前のJPAエンティティ検証（`@Size`等）が走り、`ConstraintViolationException` エラーが発生。
* **解決策（DTOの分離）**:
  * 画面入力値を受け取る **`RegisterForm.java` (DTO)** と、DB保存用の **`User.java` (Entity)** の役割を分離。
  * 画面用の文字数制限（8〜20文字）や英数混在チェックは `RegisterForm` 側で行い、`User` エンティティからはDB保存時のエラーを防ぐため桁数制限等を解除。
  * これにより、安全な入力チェックと暗号化パスワードの確実なDB保存を両立。

### 3. テストコードの拡充
* **正常系テスト**:

  ## 追加機能とエラー解決記録 (2026/07/28 - ログイン制限とアカウントロック)
ログイン失敗回数のカウント処理、一定回数でのアカウントロック機能、およびパスワード再設定機能を実装しました。

### 1. アカウントロック機能とパスワード再設定の実装
* **連続失敗カウント**: ログイン失敗ごとに `failedAttempt` カウントを +1 加算。
* **アカウントロック**: 失敗回数が 3 回に達した場合、`accountNonLocked` を `false`（DB上は 0）に更新しアカウントを自動ロック。
* **ロック解除 / リセット**: ログイン成功時またはパスワード再設定時に失敗回数を 0 にリセットし、ロックを解除。

---

### 2. JPA UPDATEクエリにおけるトランザクションエラー解決
* **事象・エラー**:
  * ログイン成功時や失敗時に `resetFailedAttempts` 等の UPDATE クエリを実行すると `InvalidDataAccessApiUsageException: Executing an update/delete query` (500エラー) が発生。
* **原因**:
  * Spring Data JPA において、`@Modifying` や `@Query` で定義した UPDATE / DELETE SQL はトランザクション境界内（`@Transactional`）で実行する必要があるため。
* **解決策**:
  * `UserRepository.java` インターフェース（または各更新メソッド）に `@Transactional` アノテーションを追記し、DB更新処理に正しいトランザクションを確保。


### 3. ログインエラーメッセージの動的切り替えと条件分岐 (2026/07/29)
* **事象・課題**:
  * 従来の実装では、1回目のパスワード誤入力でも3回目のアカウントロックでも一律で同じ統合エラーメッセージが表示されていたため、ユーザーが現在の状況（まだ間違えられるのか、既にロックされたのか）を判別しにくい課題があった。
* **原因**:
  * Spring Securityの標準設定である `.failureUrl("/login?error")` を使用していたため、認証失敗の理由（パスワード不一致／アカウントロックなど）に関わらず、すべて一律のURLパラメータに丸められて画面に遷移していたため。
* **解決策**:
  * **Java側（`SecurityConfig.java`）**:
    * `.failureUrl` を廃止し、`.failureHandler` による独自の認証失敗処理をラムダ式で実装。ログイン失敗時の例外オブジェクト（`exception`）を解析。
    * 失敗理由がアカウントロック（`LockedException`）の場合は `?error=locked`、パスワード間違いの場合は `?error=wrong` とURLパラメータを動的に切り替えるロジックを構築。
  * **画面側（`login.html`）**:
    * Thymeleafの `th:if="${param.error != null and param.error == '...'}"` を活用し、URLパラメータに応じたメッセージの条件分岐処理を実装。
    * **1〜2回目の失敗**: 「ユーザー名またはパスワードが正しくありません。」と表示。
    * **3回目の失敗（ロック時）**: 「入力制限に達したため、アカウントがロックされました。パスワード再設定を行ってください。」と、次のアクションを促す専用メッセージへ切り替わるよう改善。

    ## 追加機能とセキュリティ改善 (2026/07/29 - 投稿の認可制御と脆弱性修正)
ログインユーザー本人以外の投稿に対して編集・削除が行えてしまうセキュリティ上の脆弱性（認可の不備）を発見し、アクセス制御の実装に着手。

### 1. 検出された脆弱性・課題（認可の不備）
* **事象**:
  * ユーザーA（例: `testuser01`）でログインしている状態でも、ユーザーB（例: `tsubasa01`）が作成した投稿の編集・削除画面にアクセスでき、そのまま投稿を削除・更新できてしまう。
* **原因**:
  * **画面側（フロントエンド）**: ログインユーザーと投稿者の照合を行わず、すべての投稿に対して一律で「編集」「削除」ボタンを表示していたため。
  * **サーバー側（バックエンド）**: Controller の処理において「リクエストを実行したユーザー」と「対象投稿の所有者（投稿者）」が同一であるかの検証（認可チェック）を行っていなかったため。

---

### 2. 修正方針（2段階のセキュリティガード）
他人の投稿に対する不正操作を完全に防止するため、フロントエンドとバックエンドの双方でガードを構築する。

* **ガード1: 画面側（Thymeleaf）での非表示制御**
  * 投稿詳細画面および一覧画面において、`投稿者 == ログインユーザー` の場合のみ「編集」「削除」ボタンを表示するよう条件分岐を追加。
* **ガード2: サーバー側（Controller）でのアクセス制限・検証**
  * URL直叩き（例: `/posts/13/edit`）等による直接アクセスに対しても、Controller 内で「投稿者」と「ログインユーザー」を照合。
  * 他人の投稿に対するリクエストを検出した場合は、処理を実行せずアクセスを拒否（403 Forbidden またはエラーページへリダイレクト）するロジックを実装。

## 追加機能 (2026/08/06)
検索条件を選べる投稿検索機能
掲示板の投稿一覧から、特定のキーワードと一致条件を指定して投稿を素早く見つけ出すことができる機能です。

### 実装予定の項目
- マルチフィールド検索の実装
  入力されたキーワードに基づき、投稿の「タイトル」または「本文（コンテンツ）」のいずれかに合致する投稿を抽出します。

- 柔軟な一致条件の選択
  ユーザーは以下の3つの一致方式から検索の厳密さを選択できます。
  ・部分一致 (Containing)
  ・前方一致 (StartingWith)
  ・後方一致 (EndingWith)

- 検索状態の保持
  検索実行後も、入力した「キーワード」と選択した「一致方式」がフォーム内に保持されるため、条件の微調整がスムーズに行えます。

- 検索結果の一覧表示
  キーワードが空の場合は全件表示、入力がある場合のみ検索結果を表示します。

### 実装の技術的ポイント
- Spring Data JPA の命名規則を活用
  Containing, StartingWith, EndingWith といったキーワードをメソッド名に含めることで、複雑なSQLを書かずに一致条件に応じたクエリを自動生成します。

- 動的な検索ロジック
  サービス層にて、コントローラーから渡された matchType（一致条件）に応じて呼び出すリポジトリのメソッドを切り替えます。

- シームレスな一覧表示
  キーワードが空の場合は自動的に全件表示を行い、キーワードがある場合のみ検索結果を表示するようコントローラーで制御します。

### 利用方法
1. 投稿一覧画面（/posts）の上部にある検索フォームへ移動します。
2. 「検索キーワード」を入力します。
3. セレクトボックスから「部分一致」「前方一致」「後方一致」のいずれかを選択します。
4. 「検索」ボタンをクリックすると、条件に合致した投稿のみが表示されます。

## 追加機能 (2026/08/09 - いいね機能の実装（多対多リレーション）)
掲示板の各投稿に対して、ユーザーが「いいね」の登録および解除を行える機能を追加し、データベースにおける多対多のリレーション構造と操作を実装します。

### 実装予定の項目
- **中間エンティティ（`Like`）と Repository の作成**:
  - `User`（ユーザー）と `Post`（投稿）の ID を紐付ける中間テーブル（`likes`）を生成。
- **いいねのトグル（登録・解除）処理**:
  - ボタン押下時にすでに「いいね」済みであれば削除（解除）、未登録であれば保存（登録）するロジックの実装。
- **いいね件数のカウント・表示**:
  - 各投稿に寄せられた「いいね」の総件数を取得して画面に表示。
- **いいね状態に応じたUIの切り替え**:
  - ログインユーザーがその投稿に対して既に「いいね」しているか判定し、ボタンのデザイン（アイコンや色）を動的に切り替え。

### 実装の技術的ポイント
- **中間エンティティによる多対多の表現**:
  - `@ManyToMany` を直接使うのではなく、拡張性とデータ管理の観点から中間エンティティ（`Like`）を介した `@ManyToOne` × 2 の構成を採用。
- **重複登録の防止（複合ユニーク制約）**:
  - `@Table(uniqueConstraints = {@UniqueConstraint(columnNames = {"user_id", "post_id"})})` を設定し、同じユーザーが同一投稿に複数回「いいね」できないよう DB レベルで整合性を保持。
- **Spring Data JPA メソッドの活用**:
  - `existsByUserAndPost`（存在判定）や `countByPost`（件数取得）などの派生クエリメソッドを利用し、効率的なデータ操作・判定を実施。

 ### 開発中に発生したトラブルと解決の経緯(2026/08/10)
- 非同期通信化および画面の共通化に伴い、いくつかの技術的な問題に直面しましたが、以下の通り原因の特定とリファクタリングを行って解決しました。

#### 1. 共通レイアウト（`layout.html`）適用時のヘッダー・フッター消失問題
*   **問題の現象**:
    「いいね」ボタンの非同期化と同時に Thymeleaf Layout Dialect（`layout:decorate`）を用いた共通レイアウトの適用を進めたところ、画面上のナビゲーションバー（ヘッダー）やメイン領域、フッターなどの雛形（骨組み）が完全に消滅し、子画面のみのレイアウトで出力されてしまう現象が発生。
*   **原因の特定**:
    1.  親となる `layout.html` の `<head>` タグ自体に不要な `layout:fragment="head"` が付与されていたため、子画面をレンダリングする際に親のヘッダー構造全体を巻き込んで上書き破棄してしまっていた。
    2.  プロジェクトの依存関係（`pom.xml`）に、そもそもレイアウト共通化機能を有効化するためのライブラリ `thymeleaf-layout-dialect` の記述が不足していたため、Spring Boot がレイアウトの装飾命令（`layout:decorate`）を処理できず、子画面を単体HTMLとして解釈していた。
*   **解決のアプローチ**:
    -   `pom.xml` に `thymeleaf-layout-dialect` のスターター依存関係を追加し、プロジェクトを更新。
    -   `layout.html` の `<head>` タグから不要なフラグメント属性を削除し、純粋なタグに戻すことで本来のマージ挙動を復活。

#### 2. JavaScript（`fetch`）における CSRF トークン読み込みエラー
*   **問題の現象**:
    「いいね」ボタンをクリックした際、ブラウザのコンソール（Console）に「エラー: CSRFメタタグが見つかりません。」と表示され、非同期通信（POSTリクエスト）がサーバーに届かずに失敗した。
*   **原因の特定**:
    子画面側の `<head>` タグ内に個別に `<meta>` タグや `<title>` を記述したことで、親の `layout.html` が保持していたセキュリティ用の共通メタタグ（`_csrf` / `_csrf_header`）がThymeleafによって上書き消去されていた。
*   **解決のアプローチ**:
    -   子画面側の個別メタタグをすべて削除し、共通の安全な仕組みである `layout.html` の `<head>` 内に CSRF メタタグ（2行分）を一元化。
    -   子画面の `<head>` には `<title layout:fragment="title">` のみを持たせることで、親の共通メタタグを壊さずに自動引き継ぎさせるクリーンな設計へ修正。

#### 3. JavaScript のスコープと外部ファイル化（`.js`）のベストプラクティス
*   **問題の現象**:
    特定の画面（一覧画面、詳細画面）でのみ使用する非同期通信の処理を、共通の `layout.html` に直接記述すると、ボタンが存在しない他の画面（ログイン画面など）でも不要にスクリプトが走り、エラーやパフォーマンス低下の懸念があった。
*   **解決のアプローチ**:
    -   `src/main/resources/static/js/like.js` としてフロントエンドロジックを完全外部ファイル化。
    -   `layout.html` の `</body>` 直前に `<th:block layout:fragment="script"></th:block>` という「独自の通り道（受け皿）」を用意。
    -   `list.html` および `detail.html` の末尾（`content` フラグメントの閉じタグの外側）から、その専用の通り道に向けて `<script th:src="@{/js/like.js}"></script>` を流し込むことで、**「必要な画面のときだけ安全に外部JSを読み込む」**プロ仕様の画面共通化設計を実現。

#### 4. 投稿削除時の外部キー制約違反（Status 500）エラー
*   **問題の現象**:
    「いいね」がついている投稿に対して、削除ボタン（Deleteリクエスト）を送信した際、Spring Boot から `DataIntegrityViolationException`（外部キー制約エラー）が発生し、削除完了画面への遷移が強制ブロックされた。
*   **原因の特定**:
    データベース側で、親データ（`Post` / 投稿）と子データ（`Like` / いいね）が中間テーブルの構造（多対多）で強固に結ばれていた。親である投稿だけを先に消去しようとすると、紐づく「いいね」が迷子（データ不整合）になってしまうため、DBの安全装置によって処理が中断されていた。また、JPAの `Post.java` 側に `Like` を受け取るリスト定義自体が欠落していた。
*   **解決のアプローチ**:
    -   `Post.java` および `User.java` エンティティの最下部に、中間エンティティ `Like` をマッピングする `@OneToMany` リレーションを追加。
    -   JPA の機能である `cascade = CascadeType.ALL` および `orphanRemoval = true`（連動削除）を追記し、**「投稿（またはユーザー）が削除された際、紐づいている関連のいいねデータも自動的にすべて道連れ削除（カスケード削除）する」**ように設計を変更。これによりデータ不整合を防ぎ、正常な削除処理を達成。
