# 掲示板アプリケーション (bulletinboard)

## 0. プロジェクトの目的
- Spring Boot を使用した Web アプリケーション開発の学習
- Java によるサーバーサイド処理と、画面表示（フロントエンド）の連携の流れを理解する

## データベース設計の自動化について
本プロジェクトでは、学習の効率化のため `spring.jpa.hibernate.ddl-auto` 設定を利用し、JavaのEntityクラスからデータベーステーブルを自動生成しています。

*   **意図**: 本来必要なSQLによるテーブル作成手順を自動化することで、Javaによるサーバーサイド処理や画面連携の実装に集中するためです [1, 2]。

## 開発中に発生したエラーと解決記録（2026/07/21）


Spring BootとMySQLの連携にあたり、以下の3つのエラーに直面し、それぞれ解決しました。

### 1. MySQLドライバーの未検出エラー
* **事象**: `Cannot load driver class: com.mysql.cj.jdbc.Driver`
* **原因**: 初期設定の `pom.xml` にMySQLと接続するためのライブラリ（JDBCドライバー）が用意されていなかったため、JavaとMySQLが通信できませんでした。
* **解決策**: `pom.xml` に `mysql-connector-j` の依存関係を追加し、システム間の「通訳」を配置しました。

### 2. 旧バージョン用Hibernate方言（Dialect）の廃止エラー
* **事象**: `Unable to resolve name [org.hibernate.dialect.MySQL8Dialect]`
* **原因**: `application.properties` に記述されていた古い形式の方言設定（MySQL8Dialect）が、使用している新しいバージョンのHibernateで完全に廃止・削除されていたためです。
* **解決策**: 設定を最新の共通規格である `MySQLDialect` に変更（または削除による自動判別化）し、新しい言語変換に対応させました。

### 3. MySQLセキュリティによる公開鍵の回収拒否エラー
* **事象**: `Unable to open JDBC Connection for DDL execution [Public Key Retrieval is not allowed]`
* **原因**: MySQL 8.0以降の安全対策により、Java側からの暗号化通信用「公開鍵」の自動要求がデフォルトでブロックされたため、ログインを門前払いされました。
* **解決策**: 接続URLの末尾に `allowPublicKeyRetrieval=true` を明示的に追記し、安全なアクセス鍵の回収を許可しました。

## 開発中に発生したエラーと解決記録（2026/07/22）
* **事象**:新規投稿ページで投稿内容を入力し、投稿ボタンをクリックしするとページエラー
* **原因**PostController.javaの新規投稿保存するメソッドにHTTPリクエストを受け取るためのアノテーション（@PostMapping）が抜けていため、新規投稿ボタンを押しても保存処理が走らなかった。
* **解決策**: 新規保存メソッドの上に@PostMappingを追記。

## 追加機能と仕様変更 (2026/07/28)
ユーザー登録時の入力チェック（バリデーション機能）を追加し、安全なデータ登録が行えるよう改善しました。

### 1. ユーザー登録の入力バリデーション追加
* **ユーザー名**:
  * 必須チェック
  * 4文字以上10文字以内
  * 半角英字と半角数字の【両方】を含む英数字のみ
* **パスワード**:
  * 必須チェック
  * 8文字以上20文字以内
  * 半角英字と半角数字の【両方】を含む英数字のみ
* **エラーメッセージ一元管理**:
  * `messages.properties` を使用し、バリデーションエラー時の文言を一括管理。

---

### 2. DTO（RegisterForm）導入による設計の最適化
* **事象・課題**:
  * パスワードを暗号化（ハッシュ化）して保存する際、ハッシュ化後の文字列（60文字）に対してDB保存直前のJPAエンティティ検証（`@Size`等）が走り、`ConstraintViolationException` エラーが発生。
* **解決策（DTOの分離）**:
  * 画面入力値を受け取る **`RegisterForm.java` (DTO)** と、DB保存用の **`User.java` (Entity)** の役割を分離。
  * 画面用の文字数制限（8〜20文字）や英数混在チェックは `RegisterForm` 側で行い、`User` エンティティからはDB保存時のエラーを防ぐため桁数制限等を解除。
  * これにより、安全な入力チェックと暗号化パスワードの確実なDB保存を両立。

---

### 3. テストコードの拡充
* **正常系テスト**:
  * 新しいバリデーションルール（英数混在等）に適合するテストデータを用いて、ユーザー登録からログインまでの一連のフローを検証。
* **異常系テスト**:
  * 数字のみ入力などルール外のデータを送信した際、DBに保存されず登録画面（`auth/register`）へ戻り、モデルにエラー情報が渡されることを検証（JUnit 5 / MockMvc）。

  ## 追加機能とエラー解決記録 (2026/07/28 - ログイン制限とアカウントロック)
ログイン失敗回数のカウント処理、一定回数でのアカウントロック機能、およびパスワード再設定機能を実装しました。

### 1. アカウントロック機能とパスワード再設定の実装
* **連続失敗カウント**: ログイン失敗ごとに `failedAttempt` カウントを +1 加算。
* **アカウントロック**: 失敗回数が 3 回に達した場合、`accountNonLocked` を `false`（DB上は 0）に更新しアカウントを自動ロック。
* **ロック解除 / リセット**: ログイン成功時またはパスワード再設定時に失敗回数を 0 にリセットし、ロックを解除。

---

### 2. JPA UPDATEクエリにおけるトランザクションエラー解決
* **事象・エラー**:
  * ログイン成功時や失敗時に `resetFailedAttempts` 等の UPDATE クエリを実行すると `InvalidDataAccessApiUsageException: Executing an update/delete query` (500エラー) が発生。
* **原因**:
  * Spring Data JPA において、`@Modifying` や `@Query` で定義した UPDATE / DELETE SQL はトランザクション境界内（`@Transactional`）で実行する必要があるため。
* **解決策**:
  * `UserRepository.java` インターフェース（または各更新メソッド）に `@Transactional` アノテーションを追記し、DB更新処理に正しいトランザクションを確保。


### 3. ログインエラーメッセージの動的切り替えと条件分岐 (2026/07/29)
* **事象・課題**:
  * 従来の実装では、1回目のパスワード誤入力でも3回目のアカウントロックでも一律で同じ統合エラーメッセージが表示されていたため、ユーザーが現在の状況（まだ間違えられるのか、既にロックされたのか）を判別しにくい課題があった。
* **原因**:
  * Spring Securityの標準設定である `.failureUrl("/login?error")` を使用していたため、認証失敗の理由（パスワード不一致／アカウントロックなど）に関わらず、すべて一律のURLパラメータに丸められて画面に遷移していたため。
* **解決策**:
  * **Java側（`SecurityConfig.java`）**:
    * `.failureUrl` を廃止し、`.failureHandler` による独自の認証失敗処理をラムダ式で実装。ログイン失敗時の例外オブジェクト（`exception`）を解析。
    * 失敗理由がアカウントロック（`LockedException`）の場合は `?error=locked`、パスワード間違いの場合は `?error=wrong` とURLパラメータを動的に切り替えるロジックを構築。
  * **画面側（`login.html`）**:
    * Thymeleafの `th:if="${param.error != null and param.error == '...'}"` を活用し、URLパラメータに応じたメッセージの条件分岐処理を実装。
    * **1〜2回目の失敗**: 「ユーザー名またはパスワードが正しくありません。」と表示。
    * **3回目の失敗（ロック時）**: 「入力制限に達したため、アカウントがロックされました。パスワード再設定を行ってください。」と、次のアクションを促す専用メッセージへ切り替わるよう改善。

    ## 追加機能とセキュリティ改善 (2026/07/29 - 投稿の認可制御と脆弱性修正)
ログインユーザー本人以外の投稿に対して編集・削除が行えてしまうセキュリティ上の脆弱性（認可の不備）を発見し、アクセス制御の実装に着手。

### 1. 検出された脆弱性・課題（認可の不備）
* **事象**:
  * ユーザーA（例: `testuser01`）でログインしている状態でも、ユーザーB（例: `tsubasa01`）が作成した投稿の編集・削除画面にアクセスでき、そのまま投稿を削除・更新できてしまう。
* **原因**:
  * **画面側（フロントエンド）**: ログインユーザーと投稿者の照合を行わず、すべての投稿に対して一律で「編集」「削除」ボタンを表示していたため。
  * **サーバー側（バックエンド）**: Controller の処理において「リクエストを実行したユーザー」と「対象投稿の所有者（投稿者）」が同一であるかの検証（認可チェック）を行っていなかったため。

---

### 2. 修正方針（2段階のセキュリティガード）
他人の投稿に対する不正操作を完全に防止するため、フロントエンドとバックエンドの双方でガードを構築する。

* **ガード1: 画面側（Thymeleaf）での非表示制御**
  * 投稿詳細画面および一覧画面において、`投稿者 == ログインユーザー` の場合のみ「編集」「削除」ボタンを表示するよう条件分岐を追加。
* **ガード2: サーバー側（Controller）でのアクセス制限・検証**
  * URL直叩き（例: `/posts/13/edit`）等による直接アクセスに対しても、Controller 内で「投稿者」と「ログインユーザー」を照合。
  * 他人の投稿に対するリクエストを検出した場合は、処理を実行せずアクセスを拒否（403 Forbidden またはエラーページへリダイレクト）するロジックを実装。
